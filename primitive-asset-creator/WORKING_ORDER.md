The gateway records tool activity automatically; report external search, vision and generation honestly. Heartbeat at least every 30 seconds; a five-minute silence interrupts the active tile. Finish the workspace with a truthful outcome and note. Each plus invitation is isolated; never use another workspace's key or IDs.

The owner-Site claim/key instructions later in this document describe the older signed-in queue. They are not required for a plus-tile external workspace. Its invitation and begin action establish the workspace directly. The gateway cannot supply your search, model subscription or image-generator credentials. Use your runner's tools and record unavailable operations as blocked. Give brief decision summaries, never private chain of thought.

## Stop and report blockers

When a required operation fails or its capability is unavailable, immediately send a heartbeat at the current monitoring stage with a short message starting `Blocked:` and the actual reason. Report a `blocked` event using the stage values advertised by `report_live_benchmark`; job phase names are not automatically monitoring-stage IDs. A heartbeat is liveness, not progress. If the gateway cannot be reached, record that locally and tell the owner. Keep a recoverable workspace active while trying a specific safe repair; if it cannot continue, finish it with `blocked` and preserve the evidence. Do not report completion without the required gates.

If a v3 outline or non-contour setting changes after depth, inspect the job and use its current version to re-record an actually reviewed existing span with `record_outline_span`. This returns the same job to `silhouette` without deleting its draft. Repeat the silhouette, lip and depth checks, then build and inspect a new immutable draft. Unchanged node-image reviews can be reused only when the applied outline and curve still match; changed points, reference or curves require new image reviews. Record the blocker, recovery and resulting model IDs.

# Outline tool: image-led workflow

The outline tool is an experimental editable panel in the Primitive Asset Workshop. It accepts an image as a visual reference; it does not itself run an LLM, edge detector, segmentation model, camera calibration or automatic 3D reconstruction.

## Evidence and view

1. Load and save the reference in the outline project. The saved image is a resized JPEG and its pixel dimensions and position in the SVG editor are recorded. The original file is not retained.
2. Choose the observed view. Perspective/unknown is the safe default. Treat occluded outlines, depth, dimensions, opposite sides, exact button counts and the back as unknown or estimated. A perspective image is not an orthographic reference.
3. Observe the image using the actual tool available to the agent. State whether the input was inspected visually, processed by an edge detector, or supplied by a person. Never claim edge extraction, tool execution, model identity, token usage, or UI actions that did not happen.
4. For each part decide whether it is a supported primitive or a custom outline. Name the part, the observation and uncertainty. One profile produces one panel; a whole assembly requires separate components and constraints.

## V3 two-pass silhouette and span ledger

The silhouette working order is:

> Silhouette is two passes. Coarse: trace the primary masses in the chosen view and name them. Detail: walk the outline in running order; for each span record part, edge features at both ends, corner type, width role, surface intent, detail hint and evidence. Ask what objects of this category typically show along this outline that you have not placed, and place or reject each one. Every node must begin or end a named feature. There is no fixed node target; detail follows from named features. After every geometry change, render the saved model and inspect it.

Discover the actual tool schemas first. New v3 work opts in with `start_primitive_job` argument `job_schema_version: 3`; omission retains the legacy v2 contract. Existing v1/v2 jobs continue under their saved contract, and an existing workspace key keeps its pinned working order. A newer public guide does not silently migrate an older job. All v3 writes use the current `job_id` and `expected_version`; inspect and retry the intended operation after a revision conflict.

Before tracing, the MCP `record_silhouette_view` tool receives flat arguments `job_id`, `expected_version`, `view` (front/back/left/right/top/bottom or perspective), `reason`, `evidence_level` (observed/category_typical/estimated), `rejected_views: [{view, reason}]` and `unavailable_views`. The raw job HTTP API nests these view fields under `selection`; do not send that wrapper to the MCP tool. Review all available six views and explain the selection. If there is no six-view set, use the actual single source view and mark the others unavailable. A perspective or generated view remains an estimate where appropriate; this selection never generates a missing reference or completes the six-view pipeline.

Trace the primary masses in the coarse pass. In the detail pass, walk the authored nodes in running order and record one adjacent span with `record_outline_span` for every a → b, including last → first. The span contains:

| Field | Accepted intent |
| --- | --- |
| `part`, `start`, `end` | Short physical-part name and consecutive zero-based authored-node indices. |
| `edge_start`, `edge_end` | step, overhang, lip, chamfer, notch, slope, bump, seam, plain_corner or unknown. |
| `corner_start`, `corner_end` | curved, sharp or unknown; inspect any applied curve override. |
| `width_role` | full, inset, protruding, separate or unknown. |
| `surface_intent` | plain, texture, hole, mound, separate or unknown. |
| `detail_hint` | Optional shape, `depth_m`, `inset_frac` and note; unknown numeric values stay null. |
| `evidence` | `level` observed/category_typical/estimated and note of at most 240 characters. |
| `views` | Supporting actual front/back/left/right/top/bottom references. |
| `review_required`, `review_note` | Explicit unresolved review and its reason, where needed. |

Then call `record_category_features` with `features` containing each considered `name`, `status` placed/rejected, matching `span_id` or span endpoints for placement, and a factual `reason`, plus an overall note. Ask which category features remain unplaced; place or reject each. There is no built-in subject part list. Category-typical features are inference, not proof of their presence on this object.

The v3 silhouette gate requires 100% perimeter coverage, every authored node as an endpoint, no overlap and the category-features answer. A straight span longer than 15% of perimeter needs explicit plain surface intent and an evidence note, or an explicit review flag and note. Features below twice the applicable edge-round distance produce merge-candidate warnings rather than a failure. Inspect the gate's node/span counts, evidence-level counts, coverage percentage and warnings. Use `edit_outline_node` for revision-checked authored-node insertion, movement or removal. Insertion/removal remaps span/category records and existing `nodeDepth` entries; inspect the result before continuing. Splits/merges retain review flags and cannot erase an already invalidated semantic span. Resolve invalidation by re-recording the affected span with an actual reviewed classification, not by repeatedly splitting or merging it. A full replacement trace clears classifications for a new pass. Conflicting sharp/curved decisions at one node block the silhouette gate until corrected; accepted sharp decisions are applied through the real curve configuration at that gate.

Saved profile snapshots created after supported end-cap features preserve the original untouched depth-band segment links, so their spans can be resolved on the new model. Older snapshots without links and other features that alter depth-band segments without preserving lineage remain unsupported; never guess face indices or assume old snapshots were repaired. Downstream width/depth suggestions and hole/mound/separate queues are proposals. Full-width intent uses the panel depth; inset/protruding intent suggests offsets; separate intent requests another object. Do not claim an offset, curve or component applied merely because it appears in the ledger. Resolve a span against the actual current saved model using the advertised span-face tool, inspect its returned exact host faces, then call a supported construction operation. Discover the object-add schema for primitive/profile components with explicit parent/host frame and transforms; re-resolve faces after geometry changes. Unsupported work remains blocked.

After every geometry change, save the new model version and inspect its actual images. Saved-geometry mutation tools automatically return eight PNGs: front and rear three-quarter, front, back, left, right, top and bottom. Use those returned images; call `render_saved_model` with the current `model_id` when a fresh rendering is needed. The renderer persists a server receipt with model/source hash, timestamp, view hashes and framing evidence; `inspection: not_asserted` expressly does not say the runner viewed or approved them. Record your separate factual visual observations. If geometry saves but rendering or its receipt fails, the saved geometry remains committed and the response/live monitor exposes `moduleWarnings`. Retain that saved model ID, record the render blocker and retry rendering; do not repeat the geometry mutation blindly and duplicate a component. Rendering is constructed-mesh evidence, never a generated source reference, topology/UV approval or a visual pass. If the PNGs cannot be inspected, verification remains blocked.

## Visual curvature review questions

After tracing and classifying the spans, new v3 jobs require a separate reference-image return and answer for every authored node before the silhouette gate. For each node, call `request_node_visual_review` with `job_id`, the current `expected_version` and `node_index`. It returns the selected source image, the node's location and current curve fraction, a question and a unique receipt. Actually inspect that image with a vision-capable tool; if your CLI returns base64, use `call request_node_visual_review @arguments.json --images-dir ./visual-evidence` to save its image and pass the resulting file to that tool. Do not mistake receiving or saving an image for looking at it. Then call `record_node_visual_review` with the current version, the same node and `answer: {receipt_id, decision, radius, note}`. Choose `keep`, `sharper`, `smoother`, or `unknown`; radius is a fraction of the shorter adjacent edge, and unknown uses null. The proposed radius must agree with the direction of change and the span's sharp/curved corner classification; revise conflicting records after reviewing the source. Missing, stale or unknown node answers block advancement. The gate applies accepted node radii to the saved outline and checks geometry. If points, source image or curve settings change, request fresh images and decisions. Existing jobs created before the per-node contract retain their original order. Image-return receipts and the answers are server-recorded, but actual perception and image interpretation remain agent-reported and cannot be independently guaranteed. After a saved geometry change, inspect the actual returned model renders.

Before a connected-face feature ask two separate questions: (1) Should its outline corners be sharper or smoother than the default, and by how much? (2) Should the lip transition into the hole or mound be sharper or smoother than the desired curved default, and by how much? Record which image and feature supports each decision. `corner` controls the 2D outline independently. For connected planar faces, `apply_saved_face_feature` accepts `lip: curved|sharp` and `lip_fraction` (0.05–0.5 of depth); a curved lip defaults to 0.25, with the effective radius and any limit reported in the result. It creates a four-segment transition and UV seams between perimeter wall segments. Inspect actual renders and audit UVs; a rendered image is not proof the runner inspected it. These feature-specific questions are not yet enforced by a separate server gate.

For cross-depth curvature, inspect front and top references when available. For every node or node group ask whether and by how much it must move inward or outward across depth. Use `configure_outline_node_depth` and `record_depth_contour_review`, then inspect a render. Mark unavailable images and unsupported changes unknown; report actual observations without inventing vision calls.

## V3 lip, cross-depth contour and extrusion reviews

The v3 job order after the silhouette check is `lip_preflight → depth → depth_contour → extrusion_review → surface`. These are job phases; retain the actual current job version returned after every write. Legacy v1/v2 keep their saved phase order.

First ask whether a lip is observed, not observed or unknown, and identify its actual host: whole local end-cap, localized depth-band/face region or separate board/component. Record available view evidence with `record_primitive_lip_view`; missing views stay unavailable. A single perspective source can carry its real observation without inventing six orthographic reviews. `lipDecision` uses `recess`, `protrusion` (v3 depth-band only), `not_observed` or `unknown`. Unknown blocks progression. `not_observed` means not seen in the supplied evidence, not proof that hidden surfaces have no lip. Do not leave an applied cap recess while claiming no observed lip.

The whole-end-cap operation `configure_outline_shape` with `cap_recess` deforms existing cap vertices and scales recess depth with panel thickness. A depth-band lip is a different host: never substitute `full_endcap` for it. For a v3 classified hole/mound span, call `request_lip_visual_review` with `job_id`, current `expected_version`, `view` and `span_id`; inspect the actual returned image, then record `lip_decision` with `target: depth_band`, `spanId`, `visualReceiptId`, `decision: recess|protrusion`, the matching source and view, `curve: curved|sharp`, a host description, `board: integral|none`, `boardThickness: null`, and `curveRule: follow_silhouette`. The gate records a pending decision, not completed geometry. After final depth and contour review, build the exact span with `apply_profile_band_relief`; provide its source and result IDs to the extrusion review, inspect the returned renders, and use the render receipt. The extrusion gate requires the actual operation and the same in/out and curved/sharp choice. If the image, span or surface is unsuitable, report a blocker rather than a fabricated decision. The returned image receipt records preparation; inspection remains agent reported.

`apply_profile_band_relief` operates on one profile object and the exact authored-span triangles. The selected surface must be a connected single-boundary patch with current lineage. It moves the selected patch in or out along local surface normals and joins its original boundary with a four-segment curved cove or sharp wall; it preserves span lineage and unwraps the added wall edges as separate UV strips. The `inset` input limits the cove width; it does not shrink the floor footprint or satisfy a recorded `detail_hint.inset_frac`. Use another supported tool or mark that inset requirement blocked. It can follow non-planar bends but is bounded: it does not bridge two separate mirrored objects, supply an independently drawn footprint, fit images automatically, handle arbitrary branching/multiple-loop hosts, or prove global/inter-object collision freedom. It rejects collapsed, folded and sampled same-object crossing cases. `normalBlend` of 1 follows local normals; lower values blend toward the band-average direction to avoid a fold or reduce floor UV distortion, while retaining the requested in/out sign on each selected triangle. Report the actual blend and visually inspect the change against the reference; a heavily blended direction is not an exact normal offset. Inspect all eight result views and the actual UV audit; a warning or failed atlas remains visible. Review UV orientation, seams and clearance separately. For the surface detail shape itself, planar `apply_saved_face_feature` still provides explicit silhouette, rectangle, circle and cross choices. Independent board thickness, custom lip curves and unsupported hosts remain blocked. Separate boards may enter a v3 `add_scene_object` queue; a queue is not a built board.

After final depth, inspect front and top references where available and classify every authored node, either individually or in nonoverlapping groups, as cross-depth deformation needed yes/no/unknown. This is different from two-dimensional corner rounding and from hole/mound extrusion. Use `configure_outline_node_depth` to apply actual supported controls before recording a yes decision as complete:

| Input | Actual contract |
| --- | --- |
| `project_id`, `expected_updated_at`, `reason` | Owned closed source, exact current revision and short observation. For a linked v3 job, controls are allowed after depth in `depth_contour`, `extrusion_review` or `surface`. |
| `node_depth` | Full replacement list, with each authored `node` at most once. Include all eight offset fields for each node; an empty list clears controls. |
| `startX`, `endX` | Fractions of extrusion thickness. |
| `startZ`, `endZ`, `midZ` | Fractions of silhouette length. |
| `startY`, `endY`, `midY` | Fractions of silhouette height. |
| Offset range and curve | Every offset is −0.15…0.15. Middle Z/Y add a quadratic arc to endpoint interpolation. There is no `midX`, arbitrary multi-knot contour or automatic image fitting. |
| Optional `depth_shape` | Shared start/end/bottom/top scales 0.8…1.2 and middle rise −0.1…0.1; omitted preserves it, null removes it. |

The generator checks real geometry and conservative source-triangle orientation; folds or rotations reaching 90 degrees are rejected. This does not prove global intersection freedom, physical measurements, UV quality or reference fit. For v3, the MCP operation also builds/renders a new immutable draft and returns an updated `job.version`; use that version and inspect the returned PNGs. A source-only API response is not a saved-model visual review.

Call `record_depth_contour_review` with `job_id`, `expected_version` and `review`. Supply `review.views` for all six named views, plus perspective only for the actual single-source fallback; every row has view, observed/generated/unavailable source and note. Supply `review.nodes` groups covering every authored node exactly once, with `nodes`, `needed` yes/no/unknown, `source_views`, note and `control_proposal`. A yes proposal has all eight bounded offsets and at least one nonzero value, and must exactly match current saved `nodeDepth`. No/unknown proposals are null. A no decision without both front and top references requires `uncertainty_note`, and cannot conflict with existing nonzero controls. Cite the available front/top views for contour decisions. Unknown remains blocked. Supply `visual_review: {model_id, render_receipt_id, note}` only after actually inspecting that current model's server-rendered images; the gate verifies source/control/hash lineage while the visual observation stays agent-reported.

Next review extrusion across every depth-band span and every other visible face region. `record_depth_band_review` receives `review.views`, `review.spans`, `review.face_regions` and `review.visual_review`. Account for every stable span ID exactly once with direction `none`, `in`, `out`, `separate` or `unknown`, supporting actual `source_views`, note and target. Each available view also declares `other_surfaces` none/regions/unknown and `region_ids`; every named other region must appear in `face_regions` and cite that same view. Use unavailable rows with unknown other surfaces and empty region IDs, not fabricated coverage.

For `in`, `out` or `separate`, target includes the exact owned source `model_id`, `object_index`, current `face_indices` and resulting immutable `result_model_id`. Resolve the current span and inspect its real faces; never guess IDs. Use `apply_profile_band_relief` for its supported exact authored-span recess/mound, `apply_saved_face_feature` for supported connected planar holes/mounds, or `add_scene_object` for an explicitly linked separate part. Then record the actual result and inspect its renders. The gate requires server operation receipts matching those exact source faces or span triangles, operation, result and rendered ancestry; supplying IDs or a plan alone cannot pass. A band operation may use the exact span triangles when they cross a polygon boundary. General curved/multiple-loop hosts and unsupported localized shapes remain blocked. A previously accepted hole, mound or separate span cannot be silently downgraded to none; correct its semantics only after actual evidence review. Finish with the current result model/render receipt and a factual visual note. Unknown decisions or unknown other surfaces remain blockers, and generated or missing references retain their uncertainty even after a geometry check passes.

## Agent tools and coordinates

The workshop's connected MCP server can create an outline project from a JPEG reference, list projects, inspect a project and return its image, and accept `edit_outline_step` actions. Use `configure_outline_shape` to set panel depth, mirrored pair width, mirror state, the deterministic curve rule, and validated whole-perimeter rounding (`edge_round`). Inspect reports the per-point decisions. These controls do not enable unsupported 3D loop or feature operations. Each action requires the current `updated_at`; a conflict requires reinspection. Actions are `begin`, `point`, and `finish`, with an observed reason. Each accepted action is saved. An unfinished draft does not replace the last closed panel.

The inspector reports the image rectangle in SVG coordinates. Map a displayed image pixel to the outline as follows:

- model x = image x + pixel x / pixel width × image width
- model y = −(image y + pixel y / pixel height × image height)

This aligns to the displayed image, not to physical metres. No image-plane calibration is performed. The editor can replay saved action states. Replay is not a capture of physical mouse movements unless actual cursor events are explicitly recorded.

## Shape and validation

See [Shape creation and UV guide](SHAPE_GAUNTLET.md) for the shared layers and capability boundaries.

Points must form a closed, non-self-intersecting outline. The panel supports deterministic corner rounding based on turn angle, convex/concave classification, curve size and per-point overrides. These rules operate on a drawn contour and do not interpret the image. The shared 3D inspector can select edge loops and side-wall face bands and experimental quad-cap bands; legacy triangular caps stop selection, and transition poles limit regular flow. The outline generator alone does not infer or cut general image features. For supported connected planar hosts, `apply_saved_face_feature` can create an actual hole/recess or mound on a saved model; inspect its host and result. Curved hosts, general creases and automatic arbitrary-image reconstruction remain unsupported. The panel depth and mirror separation are adjustable; mirrored copies in the main scene become independent objects. The preview's arcade parts are fixed estimates. The 3D assembly and its separate model-library save are separate from the outline project.

The UV geometry test checks overlaps, bounds, degeneracy and distortion after the curve is generated. The six-view orientation report is diagnostic and uses provisional world axes. It does not repair UVs, prove object semantics, or guarantee readable artwork.

## Individual-node curvature decisions

Use `set_outline_node_curvature` for one node in a saved outline project. Supply its current project revision, zero-based node index, a radius fraction from 0 to 0.4 and/or inward/outward bias from −1 to +1 (null clears that setting), and an evidence-based reason. The tool validates the result and records the action. Reinspect after changes because indices are not stable IDs. The 3D workshop exposes the same local curve amount and in/out bias with numbered control-node guides and on-object drag handles. The bias does not switch a convex corner to concave. This adjusts the 2D outline corner, independently of end-edge rounding across depth.

The service does not run image or shape detection. An agent can examine a supplied image with its actually available tools and decide whether to change a node; it must record the real source and not invent usage. See [SHAPE_GAUNTLET.md](./SHAPE_GAUNTLET.md#individual-outline-node-decisions-in-the-workshop) for current behavior, limits and validation.

The read-only MCP tool `analyze_outline_topology` can propose additional points and world-axis connections on the saved control polygon; supply the actual world matrix for a transformed scene, otherwise it uses identity. These are guides only and do not form a cap quad mesh. See the topology proposals section of the gauntlet; do not report them as generated mesh loops.

The `cap_uv` setting chooses `strips` or experimental `silhouette` (curved bands remain with the face). Always inspect the UV audit: the arcade silhouette candidate currently fails stretch and is not ready for painting. The mesh uses continuous rows only for supported one-interval horizontal slices; other outlines fall back to transition patches.

## Reference candidate questions and selection

Before choosing a search image, inspect a batch of actual candidates with your available vision tool and call `review_reference_candidates`. Record the real query, source/image URLs, inspection method/tool, image dimensions when known, and an evidence note for each image. The tool asks these exact questions with `yes`, `no` or `unknown` answers:

1. Does this show the requested object?
2. Are any people visible in the image?
3. Is any part of the object obscured?
4. Is any part cut off by the image edge?
5. Is the front clearly visible?
6. Is a side clearly visible?
7. Is the top clearly visible?
8. Is the object sharp enough to trace silhouette and details?
9. Can the object boundary be separated from the background?

Declared people, occlusion, clipping, object mismatch or blur reject a candidate. Missing visual inspection or unknown critical answers leave it unresolved and prevent selection. The tool ranks supplied observations; it does not fetch images, detect people or independently verify the answers. Review and select a usable candidate with a factual reason. Prefer a clean, complete front/side three-quarter view. Front, side and top coverage are the priority three views; missing coverage remains explicit rather than being filled with guessed geometry. Repeated reviews use the returned review ID/current revision and remain scoped to the same workspace. This new report does not retrospectively change the gates of an older job.

For an attachment request, skip web search and assess the actual saved attachment with its reference name. If the attachment is rejected, record why and request a suitable replacement; do not silently substitute a search result.

Optional segmentation or depth tools are the agent's choice when actually available. A mask may help separate a clear object's boundary; it cannot recover an obscured or clipped object. A depth estimate is not a calibrated dimension or proof of hidden geometry. Record the actual tool/provider, input, output, uncertainty and validation. No segmentation/depth model or paid service is installed or invoked by the candidate-review tool.

## Generated six-view reference

A single perspective image does not determine its hidden views. Use `prepare_multiview_reference` on an owned saved image project to get the generic 3-column × 2-row prompt and source revision. Inspect the source image with the available image tool. For a name-based external workspace, first inspect `list_shared_reference_sets`; explicitly choose a suitable set with `adopt_shared_reference_set`, inspect all copied views and use the selected copied view project for a v3 job. The original generated views remain unverified and may not match the object; a changed source revision is disclosed. Attachment requests retain their supplied reference and cannot substitute a shared set. If no suitable set exists and an actual image-generation tool is available, attach the source and request the sheet; otherwise record generation as blocked and use the single-source continuation. The workshop itself does not call ChatGPT image generation or search the internet.

The layout is FRONT, BACK, LEFT on the first row; RIGHT, TOP, BOTTOM on the second. Import the complete 16:9 sheet in the silhouette workspace, inspect the whole sheet and each crop, then save the linked set and select a view. The 3×2 crop uses exact pixel boundaries. Alternatively an agent can crop the sheet and call `create_multiview_reference_set` with all seven PNG/JPEG images, their dimensions, `sheet_hash` (the SHA-256 of the UTF-8 sheet data URL) and the unchanged source revision. A second import mode accepts exactly six independent PNG/JPEG images labelled front, back, left, right, top and bottom: no sheet or grid is required, and the images may have different dimensions. Supply `images_hash` instead: SHA-256 lowercase hex of `VIEW_ORDER.map(view => view + '\n' + dataUrl[view]).join('\n')` encoded as UTF-8, where VIEW_ORDER is front, back, left, right, top, bottom. The JSON API names these digests `sheetHash` and `imagesHash`. Independent imports validate PNG/JPEG headers and encoded dimensions; this is not image decoding or a check of the pictured content. The set reports `layoutType: independent`, `sheetHash: null`, `imagesHash`, and `sheet: null`; do not synthesize a sheet. Each image must be at most 1600 pixels per dimension and 450,000 data URL characters. External agent requests remain capped at 3,400,000 UTF-8 bytes total: reduce real files locally if necessary, preserving their view identity, and retry only after correcting an oversize error. Saving is atomic; the set records owner, source, revision, hash and view label. Each view is a fresh outline project. A sheet project cannot be used as a silhouette job; choose a cropped view.

Generated panels are **unverified estimates**, not calibrated orthographic measurements. Labels and crop dimensions do not prove the generator placed the correct view in each panel, that the object stayed inside each cell, that its proportions agree between panels, or that hidden details exist. Inspect and reject incorrect panels. Do not treat generated pixels as exact 3D coordinates or claim a model or a UV has been created by this step.

## When this runner cannot generate the views

`prepare_multiview_reference` returns the actual generation prompt, pinned source project/revision, layout and `generatorFallback` instructions. It prepares a request only. If this runner lacks image generation and no suitable shared set was adopted, export the real source image (using `inspect_outline_project`) and the prepared prompt to a capable generator or ask the owner to run it. Do not pass the workspace key or service credentials to a second provider. An active invitation remains bound to its original declared provider/model.

Keep `generate_views`/`wait_views` blocked or awaiting external output until the artifacts actually return. A copied request is not automatic dispatch. The capable generator returns six actual labelled PNG/JPEG images (or a real sheet plus its six exact-grid crops) to the original authenticated runner; that runner inspects them, computes the applicable images or sheet hash and calls `create_multiview_reference_set` with the unchanged source revision. Then inspect the saved set before tracing. The independent return contract is six actual images: front, back, left, right, top and bottom. The legacy grid contract remains seven images including the real sheet. Both remain agent-supplied, visually unverified evidence until reviewed.

If only front, side and top are available, record those three as partial priority evidence and keep the six-view pipeline unresolved. Do not duplicate one image into the missing cells. Neither the original perspective photo nor a projection/render of the current model is a generated reference. Optional depth or segmentation output does not replace generated or observed views.

While the original runner is truly alive it may maintain its lease with real heartbeats. If the workspace expires or ends, obtain a linked retry key and retain source/generation lineage; do not silently resume an expired session. Continue independent available checks and give the exact blocker rather than claiming a finished reconstruction.

### V3 continuation from one real reference

Missing image-generation capability blocks the generated-reference module; it does not require abandoning every supported modelling operation. For a new opt-in v3 job, start from the actual saved source, accept the reference before tracing as required, and call `record_silhouette_view` with the source's actual perspective or side view and all other views unavailable. Follow the two-pass silhouette and complete adjacent-span/category ledger. 4. Once the workshop job exists, call `report_live_benchmark` with `action: attach_job` and its owned `job_id`. The viewer then polls its saved outline and saved draft, UV and reference set; this is a delayed saved-state view, not a video stream of the agent's screen.
5. Report the real `tool` and stable `callId` on results. Supply token counts only when the provider returns them, otherwise leave fields null. Calls without a `callId` and tool name are not counted. If the run version conflicts, inspect and retry the same `eventId`; duplicates are not added.
6. Finish the run with its actual result: `completed`, `failed`, `blocked` or `interrupted`. Completion requires the independent build gates; a monitoring record is not a completed asset.

## Queued build requests

`list_build_requests` lists saved owner requests; `inspect_build_request` returns the request and, for image mode, the actual reference image. A `name` request requires finding a reference; an `image` request uses the supplied image and skips web search. Retry creates a new request linked to the prior request with the same source and instruction. Requests are queued records; listing a request does not start work. An authenticated claimant can use the claim and lease tools described below, but there is no automatic dispatcher. Never claim an agent ran, a file was produced or a quality gate passed without corresponding evidence. Continue to use the actual run and job reporting tools when an agent performs a request.

## Claiming an existing request

A Site owner can create and revoke agent identity keys in the live monitor. A claimant with the existing authenticated Site connection can call `claim_build_request` with `request_id` and `agent_key`; the stored key label is used for attribution. This verifies possession of an owner-issued key, not the human or model behind it. Keys alone do not grant Site access. A legacy claim may instead use `agent_label`, which is caller supplied and marked as reported. The response includes a one-time per-claim `leaseToken`; keep both secrets private. Call `update_build_claim` with `action: heartbeat` before the 120-second lease expires, providing both the lease token and the same agent key when the claim was key-verified. Revocation prevents further updates. Finish with `action: finish`, a `completed`, `blocked` or `failed` outcome and an evidence note. A completed claim is a worker report, not a validated model. If a lease expires, queue a new retry rather than continuing the expired claim. Claiming does not start an agent and these calls require a working Site-authenticated connection.

## Linking a claimed request to its live run

After claiming and before research, call `start_request_benchmark` with `request_id`, `claim_id`, and `lease_token`; include `agent_key` if the claim used one. This creates or returns the same run for the active claim and links it to the request. Keep both secrets private. The monitor can open that linked run from the request. Report actual activity with `report_live_benchmark`, including search only for name inputs; image inputs use the saved attachment and skip search. Renew the claim before it expires, and finish both the run and claim with an honest outcome. A run record and a claim do not launch an agent or prove asset quality. An expired claim cannot start or resume a run; create a retry.
