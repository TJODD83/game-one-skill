# Primitive Asset Creator — external agent working order

## Browser screenshot and evidence on every project prompt

At the start of each prompt concerning this project, capture and inspect a fresh screenshot of the actual browser page at https://adaptive-uv-ao-lab.tjodd.chatgpt.site/editor/live-dashboard, if your runner has authorized browser access. After changing or checking the application, capture the relevant visible state again and include its evidence reference, timestamp, page URL, run/model ID, and server revision in the work record. Capture additional scroll positions as needed. In ChatGPT computer-use, `mcp__cua_repl.js` can select the app tab via `cua.getTab` and take the whole page with `tab.screenshot({fullPage:true})`, or the viewport with `tab.getScreenshot()`; other runners must use their own available browser screenshot tool. These tools are not a gateway HTTP endpoint. If browser access or screenshots are unavailable, record that blocker; never present a server-rendered model, a stale screenshot, or an instruction to inspect as a fresh screenshot or completed inspection. Keep keys and private account data out of evidence. A screenshot does not by itself prove backend behavior or that an image was inspected.

Work on the single workspace in the owner's handoff packet. Read this file, then the bundled [WORKING_ORDER.md](WORKING_ORDER.md), [SHAPE_GAUNTLET.md](SHAPE_GAUNTLET.md), the gateway `context` response and the current `tools` schemas. The server response is authoritative for this workspace, its input and currently available operations. Record the source revision reported at sign-in and whenever the server changes during the run; older runs without a recorded revision are unknown. The toolkit does not provide an LLM, image generator or internet search service; use the tools actually available to your runner and record any missing capability.

## 1. Connect and identify this runner

1. Obtain the gateway root URL and scoped key from the owner's **+ / copy** handoff. The entry gateway is `https://primitive-agent-entry.tjodd.chatgpt.site` unless the owner supplies an updated address. Put the URL in `PRIMITIVE_AGENT_URL` and key in a secret `PRIMITIVE_AGENT_KEY` environment variable. Do not write the key into source, git, chat, notes, command arguments, artifact names or URLs. An interactive client can read it through a hidden prompt.
2. Run `python3 primitive_agent.py login --provider PROVIDER --model MODEL --reason "Brief task summary or runner setting"`. Report the model identifier supplied by the execution environment. If unavailable, say `unknown`; do not guess. Provider/model/settings are agent-reported, not independently authenticated.
3. `reason` means a short public work summary or exposed runner setting. Never submit hidden chain of thought, internal deliberation or private reasoning transcripts.
4. Run `context` and `tools`. Retain the returned workspace, run, revision and tool schemas. Confirm the supplied object name, source mode, attachment and owner instructions. A successful connection creates a work record, not a finished object.
5. Work only within this key's workspace. Other agents may run simultaneously in their own spaces. Use other workspaces only through the owner-authorized shared reference tools described below; their source IDs identify read-only candidate sets, and adoption creates fresh local IDs. Preserve past submissions.

The client has no required third-party Python packages. Use its help for exact arguments. Requests are authenticated `POST /api` calls. Other CLI tools can implement the same JSON protocol; no browser session is needed when the gateway accepts your key.

## 2. Prepare a clean attempt

Use the new workspace and empty file allocated for this handoff. Do not reuse a prior model as if it were new. Keep input references, generated references, mesh, UV, recorded observations and output version linked to this workspace. Read the actual server context before creating projects or selecting IDs.

Send a heartbeat while actively working and before a long operation. Local work does not renew the server contact lease. While waiting, keepalive sends liveness-only heartbeats every 30 seconds for a bounded 15 minutes by default; see README commands. Read context after an interruption. Only the same valid key and exact registered provider/model may explicitly resume an interrupted unfinished running workspace, preserving its run, files and history. Active work uses heartbeat; revoked, expired or terminal work must not be resumed silently or rebound to another runner.

## 3. Find or inspect the source

- **Name input:** first inspect the owner’s shared six-view candidates. If no suitable set exists, search for the exact requested object using an actually available search tool. Record the search query, considered candidates, selected source URL, source image and why it was selected. Describe uncertain dimensions and hidden surfaces.
- **Image input:** inspect the saved attachment returned by context. Use it directly and bypass web search. Keep the original image and its provenance.
- Inspect a batch of actual images with a real vision-capable tool. Call `review_reference_candidates` with the actual query (name mode) or attachment reference name (image mode), source URLs, inspection method/tool and each image's evidence. Answer all nine questions: object match, people, occlusion, clipping, front, side, top, sharpness and background separation.
- Reject candidates with people, obscured/clipped geometry, the wrong object or blur. Unknown critical answers remain unresolved. Prefer a clean full-object front/side three-quarter image; prioritize actual front, side and top coverage. The server scores your supplied observations and does not run person detection or verify the image itself.
- Select a usable candidate with a factual reason. For a rejected attachment, request a replacement and keep web search skipped. A segmentation or depth tool is optional only if actually available and useful; log its real output and uncertainty. Neither tool recovers hidden evidence or substitutes for references.

Use the gateway's live reporting tools to record starts and actual results. When reporting events, follow the current schema, UUID/revision rules and allowed URL format. A note about a search does not execute a search.

## 4. Generate and review six views

1. For a name-based request, first call `list_shared_reference_sets`. Compare each candidate’s name, source, available views and uncertainty with the requested object; explicitly choose a suitable set or reject it. Call `adopt_shared_reference_set` with its `set_id`, `origin_session_id` (null for the owner’s own workspace) and a short reason. It copies the original source and six actual images into this key’s workspace with new IDs and an audit record. Call `inspect_multiview_reference_set` on the returned set and inspect all images. For a new v3 job use the returned chosen view’s `project_id` as `reference_project_id` so the job retains six-view provenance. Reused generated images remain estimates; if the source changed, treat the relationship as uncertain. A supplied attachment remains authoritative: do not substitute a shared set. If no suitable set exists, create an owned reference project from the actual image and continue with generation or the documented single-source fallback.
2. When no suitable shared set was adopted, use `prepare_multiview_reference` to obtain the generic instruction. Attach the source to a real available image generator. Record provider, prompt, input, start, wait, returned output or failure. If no generator is available, use the returned `generatorFallback`: export the actual source image plus exact prompt to a capable generator/owner, share no workspace key, and keep the stage blocked/awaiting returned artifacts. Copying a request does not dispatch a worker. The original authenticated runner must receive and inspect six actual PNG/JPEG views, with an actual sheet optional, then import them with the pinned source revision. Do not rebind its invitation to another provider/model. Maintain real heartbeats while waiting. Explicitly resume only an eligible interrupted workspace using its registered identity; terminal or expired invitations need a new supported attempt.
3. Review the complete sheet and each crop. Layout is **front, back, left / right, top, bottom**. Check alpha/background, exact cell boundaries, orientation, clipping, object identity and contradictory details. Generated/hidden views are estimates, not calibrated measurements.
4. Save six actual crops using the upload-views command or current multiview-set tool. Local names are front/back/left/right/top/bottom with PNG/JPG/JPEG extensions. Independent views use images_hash; an optional actual sheet uses sheet_hash and exact grid crop dimensions. Keep source revision, dimensions and labels. Do not fill missing images, fabricate a sheet or describe model renders as generated references. The README lists command options and image/request limits.
5. Inspect the saved set. Link it to this attempt through the supported job/scene APIs. Recheck all views after model changes.

Front, side and top are the priority three views. If only those exist, record partial evidence and keep the missing six-view pipeline unresolved. Never replace a missing generated view with the original image, a repeated crop or a render of the current model.

**V3 single-reference continuation:** if this runner cannot generate views, record the generation module as blocked/unverified and continue only the supported single-reference modelling path. Start an opt-in v3 job on the actual source, accept its reference in the required gate order, then use `record_silhouette_view` for the source's actual perspective or side view and mark other views unavailable. Trace both silhouette passes, record the span/category ledger and label hidden depth, hidden parts and category assumptions estimated or category_typical. Build justified geometry through the available tools, including `add_scene_object` for supported separate components, then use `render_saved_model` and inspect the returned images after changes. These are renders of your actual constructed model and require no image generator; they do not fill the missing source views. Preserve the unresolved generation, cross-view match and final-quality limits in the result.

This is the six-view module: its events, timer and last reached stage belong to this attempt. Its saved images must not appear as another agent's current reference.

Before drawing, record an observation plan for all actual reference views: name each visible or inferred feature generically, identify its upper and lower boundary on the relevant silhouette or host, intended host and direction (in, out, separate, texture or unknown), supporting views and uncertainty. Treat those two boundaries as the endpoints of the feature span; middle curve controls can still shape geometry between endpoints. List related rings, nested shapes and separate pieces as decisions rather than assuming a specific object or using a fixed parts list. For six-view sets, use `record_primitive_view` and `record_primitive_detail` where their schemas support the view, updating actual node links after tracing. Their counts and plans are agent observations, not proof of geometry. For a perspective-only source, record its actual observations in the span/category and attempt ledgers; the six named views remain unavailable.

## 5. Trace and build the main shape

The silhouette working order is:

> Silhouette is two passes. Coarse: trace the primary masses in the chosen view and name them. Detail: walk the outline in running order; for each span record part, edge features at both ends, corner type, width role, surface intent, detail hint and evidence. Ask what objects of this category typically show along this outline that you have not placed, and place or reject each one. Every node must begin or end a named feature. There is no fixed node target; detail follows from named features. After every geometry change, render the saved model and inspect it.

1. Inspect the source and choose the observed view. Keep perspective, scale and hidden geometry uncertainty explicit.
2. Create a named outline job/project with the actual source. New v3 work explicitly supplies `job_schema_version: 3` to `start_primitive_job` when that schema is advertised; omission keeps the legacy v2 contract. Respect gate order: accept/review the reference before tracing when the tool requires it. Existing jobs and invitations retain their original version and pinned order; do not silently upgrade them.
3. For v3, call `record_silhouette_view` before tracing with flat MCP arguments `job_id`, `expected_version`, `view`, `reason`, `evidence_level`, `rejected_views` and `unavailable_views` (the raw HTTP API instead nests the view fields under selection). Compare the complete available six-view set; if no set exists, record the single source view and explicitly mark other views unavailable. Missing views do not become generated evidence or a passed generation stage.
4. Make the coarse pass, then the detail pass using actual pixel-to-outline coordinates. Prefer supported batch operations for speed; record actual points and measured operation duration. Keep a closed, non-self-intersecting silhouette. For every consecutive authored node pair, including last → first, call `record_outline_span` with a short physical-part name, both end-edge features and corner types, width role, surface intent, optional detail hint, supporting views and evidence. Never add nodes merely to meet a numeric target.
5. Call `record_category_features` with the category features you actually considered. Each is placed on a recorded span or explicitly rejected with a reason; category-typical expectations are inference until supported by the references. The v3 gate requires full perimeter coverage, every node as a span endpoint, no overlapping spans and the category answer. For a straight span exceeding 15% of perimeter, explicitly justify `surface_intent: plain` in its evidence note or flag it for review with a note. Small-feature merge candidates are warnings, not permission to remove a supported feature silently. Use `edit_outline_node`; insertion/removal remaps spans and nodeDepth. Inspect inherited review flags. Split/merge cannot erase invalidated semantics; re-record the affected span after actual review. Conflicting sharp/curved node decisions block the gate; accepted sharp intent is applied through the real curvature operation.
6. For every authored node in a new v3 job, call `request_node_visual_review`, actually inspect its returned reference image, and call `record_node_visual_review` with that node's unique receipt, keep/sharper/smoother/unknown decision, radius fraction and a factual observation. Unknown or missing answers block the silhouette gate; the source image and runner's answer are recorded, while the runner's actual perception remains unverified. The gate applies the selected radii. Existing jobs without this pinned contract keep their earlier order. See the exact schema and example in `WORKING_ORDER.md`.
7. Validate the outline and ledger, then choose depth and any mirrored width based on visible evidence or an explicitly marked estimate. Read the v3 per-span width/depth proposals; they are not applied deformation.
8. Review lips, integral/separate boards and panel thickness before applying supported geometry. Use current schemas and actual tool output. A lip plan does not create a lip. Per-span corner intent must use the actual supported curvature operation; verify the resulting geometry.
9. Review each node's curvature and horizontal/vertical/angular routing against the views. Save supported per-node decisions with evidence and current revision. A connected depth station does not prove a selectable cap route or complete quad flow.
10. Check taper, curve and world/view alignment across the source images. Do not report automatic cross-view fitting when the current operation accepts manually supplied values.
11. Save an actual scene draft only through a supported constructor. After every geometry change, inspect the eight actual PNGs automatically returned by supported saved-geometry mutation tools. Call `render_saved_model` on the current model ID if fresh renders are needed. Retain its persisted render receipt and model/source hash; the receipt says inspection not_asserted, so record visual observations separately. If rendering fails after a successful save, the geometry remains committed and moduleWarnings identify the gap: retain the saved model ID and retry rendering rather than repeating a mutation and duplicating geometry. A changed and rechecked v3 outline can build a new immutable draft version while preserving the earlier model/receipt. A rendering tool response alone is not visual review, and model renders never substitute for generated source references. If rendering is unavailable, record that required verification blocked. Keep draft status until the required quality checks pass.

For v3, the checked silhouette is followed by `lip_preflight → depth → depth_contour → extrusion_review → surface`. Explicitly decide lip observed/not_observed/unknown and its whole-cap, localized-band or separate host. A whole-cap `cap_recess` is not a localized deck/depth-band lip; unsupported custom/localized/curved-host work stays blocked. Perspective source observations may be recorded honestly, with the other views unavailable.

After final depth, use `configure_outline_node_depth` for actual bounded cross-depth shaping. It replaces the complete `node_depth` list: each node has startX/endX, startZ/endZ, startY/endY and midZ/midY, all −0.15…0.15; X scales by panel thickness, Z by silhouette length, Y by height. Middle Z/Y form a quadratic arc, with no midX or arbitrary multi-knot fitting. Optional `depth_shape` supplies shared 0.8…1.2 scales and −0.1…0.1 middle rise (null clears it). The v3 MCP operation saves/renders a new immutable draft and returns a new job version; use it. Inspect actual PNGs and retain the receipt.

Call `record_depth_contour_review` for every node exactly once, individually or in groups. Supply all six view rows plus actual perspective fallback where needed; mark unavailable evidence honestly. Each group declares needed yes/no/unknown, source_views, note and null or complete eight-field control_proposal. Yes requires a nonzero proposal matching saved controls; no cannot conflict with existing controls and needs an uncertainty_note when front/top references are missing. Include actual `visual_review` model_id/render_receipt_id/note. Unknown blocks; a server receipt proves rendering, while your inspection note remains agent-reported.

Call `record_depth_band_review` for every stable span and all other relevant face regions. Each span/region declares direction none/in/out/separate/unknown, source views, note and exact target or null. Available view rows also declare other_surfaces none/regions/unknown with matching region_ids. Required operations name source model/object/face IDs and result_model_id, then must match actual server operation receipts and current rendered model lineage. Use real planar feature construction or separate-object addition; do not pass a queued plan as execution, silently downgrade an accepted hole/mound/separate intent, claim partial-face/curved-host support, or mark unknown other surfaces reviewed. The complete field contracts and remaining limits are in WORKING_ORDER.md and the advertised schemas.

## 6. Build supported details

Review visible features generically rather than inserting a fixed arcade part list. For each proposed detail, record source/view, host object, actual face/group, silhouette, location, depth/height, operation and uncertainty. Choose a supported primitive, hole, recess, mound, separate component or outline operation.

For v3, consume the ledger's hole/mound/separate detail queue as proposals. Resolve each host span to the actual current saved-model face IDs through the advertised span-resolution tool, then inspect that selection before construction. A separate-object proposal uses the actual object-add tool when available, with explicit parent/host frame, transform and linked span. These are flat saved objects with placement provenance, not a maintained articulated/nested hierarchy. Neither a queue entry, a proposed offset nor a face-resolution result changes geometry. Follow current schemas and re-resolve after a geometry revision.

Discover saved face IDs with `inspect_saved_feature_faces`: omit `face_indices`, page with `face_offset` and `face_limit` (1–500), and follow `nextOffset` until null. IDs are global for that saved mesh; do not guess later IDs from the first page or combine pagination with selection. Reinspect after geometry changes.

Check the real current capability list first. Existing planners may validate a proposed boundary without editing the mesh. Use `apply_saved_face_feature` for real recess/mound geometry on supported connected planar saved-face selections and `add_scene_object` for supported separate components. Curved/multiple-loop hosts, automatic feature placement, image-led internal layer construction and independent per-node cross-depth curves remain unsupported or unverified. Mark each missing operation blocked, retain the proposed parameters and attempt independent available stages. Never rename a planner result as built geometry.

Check actual connectivity, manifold state, degenerates, normals, intersections, intended holes, hierarchy and source alignment after changes. Keep separately moving objects separate; preserve shared connected topology where appropriate.

## 7. UV, texture and verification

1. Inspect actual UV islands, direction, bounds, overlap, degeneration, seams, stretch and density. Numerical checks do not prove paintability or appearance.
2. Preserve the shape's current supported UV policy. A face-contained circular box-hole UV mode is not a generic solution for every silhouette, cylinder, hole or mound.
3. Align the six references to the actual scene. Choose visible pixels by face orientation and occlusion; reject background and contradictory/uncertain regions.
4. Transfer or bake **albedo/base colour only** using a real supported tool. Do not bake shadows, AO, highlights, reflections or lighting into base colour. Keep AO separate.
5. To attach real prepared UV0 colour pixels, call `attach_saved_color_atlas` with model_id, actual PNG/JPEG data_url, encoded width/height and reason; color_space defaults srgb and flip_y true. Limits are 450,000 data URL characters, 1600 pixels per axis, correct 1:1 square or 1:3 portrait aspect, 50,000 geometry vertices and the saved-model size limit. The server computes the exact main packed-UV binding and saves a new immutable model/operation receipt; use its returned model ID. Inspect the eight returned untextured geometry PNGs and explicit uploaded-atlas image, then the mapped colour in a verified WebGL viewer. This does not paint/project a reference, generate PBR/AO or approve alignment. Geometry changes invalidate the atlas on the new version.
6. A 96×96 view-to-UV diagnostic is a low-resolution draft check, not a final production bake. Report its exact coverage/conflict limits. If final transfer is unavailable, record it blocked.
7. Review the saved model, atlas, source images and cross-view fit. Record the current scene/reference revisions. Geometry edits invalidate earlier checks.

## 8. Save, submit and finish

1. Save through the available model/job tools or the gateway's `submit` action using the accepted model JSON contract. Retain the returned artifact IDs, revisions and validation results. Do not submit executable code as a model.
2. Reinspect the saved submission or request a `snapshot`. Confirm that the expected output exists and belongs to this workspace.
3. Record duration, furthest actual stage, tool results, known failures and missing gates. Supply usage only when the provider returns measured numbers; use null/unavailable otherwise.
4. Send `finish --outcome completed|blocked|failed --note "Factual result and evidence IDs"`. A completed agent report does not by itself pass independent quality gates or win the leaderboard. Use `blocked` for missing required tools/gates and `failed` for an attempted operation that failed.
5. Read back the final server state. The active viewer should undock finished/expired work while retaining its attempt in history. Never delete other agents' data or clear the database to create a blank viewer.

## Stage order and live evidence

`request → search (name only) → select_reference → vision_source → generate_views → wait_views → crop_views → review_views → workspace → trace_outline → check_outline → review_lip → apply_lip → set_depth → route_nodes → shape_depth → layers → select_faces → plan_details → build_details → check_geometry → build_uv → check_uv → transfer_colour → review_texture → save_model → final_review`

For each actual operation record **started**, optional **progress**, then **completed**, **blocked** or **failed**. Keep a heartbeat for liveness. Include the real stage, current image/view, artifact/reference ID and concise evidence summary when supported. The server observes calls to its own endpoints; external search, vision and generation are agent-reported unless that provider supplies independent receipts. Do not fabricate progress percentages, screenshots, token counts, tool calls, model identity, geometric gates or a successful finish.
